# 算力运维分享文档（硬件运维主题）

## 1. 分享定位

本次分享聚焦 **“硬件运维”**，目标是让团队在 AI 智算中心场景下具备以下能力：

1. 能识别硬件故障如何影响训练任务（故障传导路径）。
2. 能建立硬件监控覆盖并设置合理阈值（可观测性）。
3. 能形成标准化处置流程（SOP）和复盘机制（闭环）。

---

## 2. 硬件运维在算力场景中的职责边界

硬件运维不只是“修机器”，核心是保证算力稳定供给，职责建议包括：

- **服务器生命周期管理**：上架、验收、巡检、下线。
- **GPU 节点健康管理**：驱动、固件、ECC、Xid、温度功耗。
- **机房基础设施协同**：供电、制冷、机柜功率、线缆规范。
- **故障处置与隔离**：坏卡、坏盘、坏网口、坏节点快速摘除。
- **容量与风险管理**：故障率趋势、备件池、RMA 周期管理。

## 3. 硬件故障传导路径（重点）

### 3.1 典型链路一：散热异常

```text
冷却能力下降 / 风道堵塞
  -> GPU 温度升高
    -> GPU 降频（时钟下降）
      -> 单卡吞吐下降
        -> 多机同步等待增加
          -> 训练 step time 抖动，整体任务变慢
```

### 3.2 典型链路二：电源波动

```text
电源模块异常 / 机柜供电不稳
  -> 节点重启或设备掉电
    -> 训练进程中断
      -> 作业重试和排队堆积
        -> 训练 SLA 违约，GPU 有效利用率下降
```

### 3.3 典型链路三：GPU 介质退化

```text
GPU ECC 错误累积
  -> CUDA/NCCL 异常
    -> 训练进程退出
      -> 作业失败重启
        -> 训练窗口拉长，影响版本发布节奏
```

### 3.4 典型链路四：PCIe/NVLink 异常

```text
PCIe 纠错或链路降速 / NVLink 异常
  -> 卡间通信带宽下降
    -> AllReduce 变慢
      -> GPU 计算等待通信
        -> 集群看似“有卡”，实际“低效”
```

## 4. 硬件运维监控体系（从可见到可控）

### 4.1 节点级监控（必选）

| 类别 | 指标 | 告警建议 |
|---|---|---|
| 温度 | GPU 温度、CPU 温度、进风/出风温度 | 连续高温触发 P2，超过保护阈值触发 P1 |
| 功耗 | GPU 功耗、整机功耗、机柜功率占用 | 突降或突增均告警，联动电源排查 |
| 稳定性 | 节点重启次数、宕机次数、BMC 事件日志 | 24h 内重复重启直接升级为 P1 |
| 介质健康 | GPU ECC、磁盘 SMART、RAID 状态 | 累积错误增长率超过阈值触发检修 |

### 4.2 GPU 专项监控（必选）

| 类别 | 指标 | 运维含义 |
|---|---|---|
| 可用性 | GPU online 数、可分配数 | 是否满足调度资源池声明 |
| 性能 | SM 时钟、显存时钟、利用率 | 判断是否存在降频和空转 |
| 稳定性 | Xid 错误码、ECC 单双比特错误 | 识别软故障与硬故障趋势 |
| 拓扑 | NVLink 带宽、PCIe 链路速率 | 判断多卡训练通信基础是否可靠 |

### 4.3 告警分级与响应时限（建议）

- **P1**：集群可用性受损（节点批量掉线、训练大面积失败），立即值班响应。
- **P2**：性能显著下降（降频、链路降速、重复 ECC），高优处理。
- **P3**：单点轻微异常（偶发告警），持续观察并安排巡检。

## 5. 硬件故障处置 SOP（值班可执行）

### 5.1 标准流程

1. **告警确认**：核验同类告警数量、影响节点范围、影响任务规模。  
2. **快速止损**：故障节点从调度池摘除，避免扩散影响。  
3. **分层定位**：BMC/系统日志 -> GPU 日志 -> 拓扑/线缆 -> 机房环境。  
4. **故障分级处理**：软件可恢复（重启驱动/服务）与硬件需更换（RMA）分开。  
5. **恢复验证**：回池前压测（短训任务 + 通信压测 + 温控观察）。  
6. **复盘沉淀**：更新故障画像、阈值、巡检项、备件策略。

### 5.2 常见故障快速决策

| 现象 | 初步判断 | 快速动作 |
|---|---|---|
| Xid 连续出现 | GPU 卡稳定性风险 | 立即摘除节点，保留现场日志 |
| 温度持续偏高 | 散热或风道问题 | 降载并检查风扇/风道/机房冷却 |
| 节点反复重启 | 电源/BMC/主板风险 | 停止调度，硬件工程师介入 |
| 多卡训练性能突降 | PCIe/NVLink 异常 | 执行拓扑与链路带宽检测 |

## 6. 团队分工（围绕硬件运维主线）

### 6.1 分头研究建议

| 成员 | 负责模块 | 本周期重点 |
|---|---|---|
| 成员 A | GPU 健康与驱动固件 | Xid/ECC 规则优化，坏卡识别标准 |
| 成员 B | 机房电力与散热协同 | 温控阈值、机柜功率、异常联动策略 |
| 成员 C | 节点验收与巡检 | 上架验收清单、巡检自动化、备件池模型 |
| 成员 D | 故障自动化处置 | 节点自动摘除/回池流程、SOP 工具化 |

### 6.2 定期分享机制

- 双周一次硬件专题分享，每次只讲一个故障域（温控、电源、GPU、拓扑）。
- 每次必须包含：
  - 真实案例（可脱敏）
  - 传导路径图
  - 指标证据截图
  - 处置与复盘结果

## 7. 近期进展汇报（按人阐述模板）

> 适用于你提出的“每个人分头讲自己负责部分”。

### 7.1 单人汇报结构（5 分钟）

1. 我负责的硬件模块是什么。  
2. 本周期完成了哪些监控/巡检/自动化改造。  
3. 发现了哪条关键故障传导路径。  
4. 已经落地了哪些改进，效果如何。  
5. 还存在哪些风险，需要谁协同。  

### 7.2 示例讲法

- **成员 A（GPU 方向）**  
  “本周期重点是 Xid 与 ECC。我们把 Xid 高频码从 P3 提升到 P2，并新增了节点自动摘除策略。过去一周 GPU 重复故障节点数量下降，训练失败重试率降低。下阶段需要和平台侧一起把回池压测自动化。”

- **成员 B（散热方向）**  
  “我们补齐了机柜温度与 GPU 降频关联看板，确认晚高峰时段存在热区。已完成风道整改和阈值重设。下阶段要推进冷热通道巡检标准化，减少季节性波动影响。”

- **成员 C（节点巡检方向）**  
  “上线了上架验收脚本和巡检报告模板，覆盖磁盘、内存、GPU、BMC 四大类。发现两台节点存在潜在电源告警，已提前更换，避免了训练窗口内故障。”
